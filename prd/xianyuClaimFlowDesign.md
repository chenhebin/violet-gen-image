# 闲鱼购买后快捷注册与兑换设计方案

- 文档版本：v1.0
- 更新日期：2026-08-13
- 适用项目：`frontAndServer`
- 适用域名：`https://img.daidaiweb.cn`
- 约束：不修改 Ydisks-Xianyu-Helper；继续使用现有兑换码体系
- 实施对象：负责修改 Vue 用户端、Go 后端、OpenAPI、Mock 和测试的执行 AI

## 1. 背景

当前闲鱼自动发货内容为网站地址和兑换码。买家需要依次完成：

```text
打开网站
  -> 注册或登录
  -> 回到闲鱼复制兑换码
  -> 在网站中寻找右上角兑换入口
  -> 粘贴兑换码
  -> 点击兑换
```

这个流程存在三个主要问题：

1. 买家需要在闲鱼与浏览器之间切换。
2. 买家需要理解“注册”和“兑换”是两个独立步骤。
3. 买家需要自己找到兑换入口，容易中途退出或向卖家咨询。

本次改造把“网站地址 + 手动兑换码”升级为带兑换码的领取链接。用户点击链接后，网站自动识别待领取的兑换码、恢复已有登录会话，并把注册、登录和兑换串成一条连续流程。

## 2. 已确定的业务决策

### 2.1 闲鱼库存格式

Ydisks 的每条库存是一整行完整发货消息。每一行只能对应一个兑换码和一个订单，不在一条库存中加入真实换行。

正式格式：

```text
浏览器打开领取并开始创作吧～：https://img.daidaiweb.cn/claim?code=YY-AKK9-XD9M-9DSM ｜ 兑换码：YY-AKK9-XD9M-9DSM
```

批量库存示例：

```text
浏览器打开领取并开始创作吧～：https://img.daidaiweb.cn/claim?code=YY-001 ｜ 兑换码：YY-001
浏览器打开领取并开始创作吧～：https://img.daidaiweb.cn/claim?code=YY-002 ｜ 兑换码：YY-002
```

说明：

- 链接中的兑换码和备用兑换码必须完全一致。
- `/claim/` 本身不包含订单对应的兑换资格，只作为手动输入备用码的入口。
- 后端导出时必须对 Query 参数执行标准 URL 编码，不能直接用字符串拼接未经编码的任意值。
- 当前兑换码字符集虽然不需要特殊转义，实现仍应使用标准 URL 编码函数。

### 2.2 领取地址

```text
https://img.daidaiweb.cn/claim?code=<完整兑换码>
```

本方案接受完整兑换码短暂出现在 URL 中，不新增一次性领取票据或 `claim_links` 数据表。

### 2.3 登录状态的判断方式

“检查浏览器缓存是否登录过”的准确实现应为：

```text
浏览器自动携带已有 HttpOnly Session Cookie
  -> 前端请求 GET /api/auth/session
  -> 后端校验会话是否存在、未过期、未撤销且账号正常
  -> 前端得到当前用户资料并回显邮箱
```

禁止从 `localStorage`、`sessionStorage` 或普通 JavaScript Cookie 中读取、保存密码或会话 Token。服务端会话是登录状态的唯一可信来源。

同一用户若从闲鱼内置浏览器打开链接，而之前是在 Safari、Chrome 或微信浏览器登录，Cookie 通常不会共享。这种情况应正常显示注册页，并提供“已有账号，去登录”，不能声称跨浏览器自动识别账号。

## 3. 设计目标

1. 已登录用户：点击链接后，只需确认一次即可领取。
2. 新用户：填写注册表单并点击“注册并领取 10 次”，后续自动完成。
3. 老用户但当前未登录：登录后自动继续领取，不要求重新复制兑换码。
4. 兑换成功后立即显示新增次数和当前余额，并提供“开始创作”。
5. 刷新、网络重试或重复点击不能重复增加次数。
6. 兑换次数必须绑定服务端用户账号，不能绑定浏览器或设备。
7. 保留原有手动兑换入口，作为链接异常和售后兜底。
8. AI API URL、Key、真实余额和兑换判断仍只能由服务端控制。

## 4. 非目标

1. 不修改 Ydisks-Xianyu-Helper。
2. 不通过闲鱼自动创建账号或发送固定密码。
3. 不新增邮箱验证码、短信验证码或魔法链接。
4. 不取消现有右上角手动兑换弹窗。
5. 不在本期引入一次性领取 Token。
6. 不让前端直接修改余额或判断兑换码最终是否可用。

## 5. 最终用户流程

### 5.1 已登录用户

```text
点击闲鱼领取链接
  -> 网站提取兑换码并立即清理地址栏
  -> 恢复服务端登录会话
  -> 显示当前账号邮箱和待领取次数
  -> 用户点击“领取到此账号”
  -> 服务端兑换
  -> 显示“已增加 10 次，当前剩余 N 次”
  -> 用户点击“开始创作”
```

必须保留一次账号确认，避免浏览器中登录了错误账号后自动绑定。页面应明确显示：

```text
额度将领取到：violet@example.com
```

同时提供“不是我的账号，切换账号”。

### 5.2 新用户

```text
点击闲鱼领取链接
  -> 网站提取兑换码并立即清理地址栏
  -> 未恢复到有效登录会话
  -> 默认显示注册表单和“注册后自动领取 10 次”提示
  -> 用户提交注册
  -> 注册成功并自动登录
  -> 前端自动提交刚才保存的兑换码
  -> 显示领取成功和余额
```

注册主按钮文案：

```text
注册并领取 10 次
```

### 5.3 已有账号但未登录

注册表单旁保留清晰入口：

```text
已有账号？登录并领取
```

登录成功后自动继续兑换。用户不需要回到闲鱼，也不需要再次粘贴兑换码。

### 5.4 无兑换码访问 `/claim`

用户可能删除 Query 参数、从收藏夹进入或只打开基础地址。此时显示手动输入页：

```text
输入备用兑换码
[兑换码输入框]
[继续领取]
```

提交后进入相同的登录检查和领取流程。

## 6. 前端设计

### 6.1 路由

在 `front/client/src/router/index.ts` 增加公开路由：

```text
/claim
```

要求：

- `meta.public = true`，否则现有路由守卫会提前跳到 `/auth` 并增加不必要的页面切换。
- 页面内部主动调用 `auth.restore()` 判断会话。
- 不新增 `/claim/:code`，正式入口使用 `/claim?code=...`。
- `/claim/` 和 `/claim` 应由前端路由或 Web 服务器统一兼容。

### 6.2 兑换码的前端生命周期

领取页首次加载时按以下顺序处理：

1. 从 `route.query.code` 读取字符串。
2. 执行 `trim()` 和大写标准化。
3. 只做格式级校验，不在前端判断兑换码真实状态。
4. 写入当前标签页的 `sessionStorage`，建议键名为 `yy_pending_redemption_code`。
5. 立即执行 `router.replace('/claim')` 或 `history.replaceState`，移除地址栏中的 `?code=...`。
6. 后续注册、登录和兑换都从 `sessionStorage` 恢复待领取兑换码。
7. 兑换成功、明确无效、已使用、过期或用户主动取消后立即删除该键。
8. 网络错误和未知服务错误时暂不删除，允许原页面重试。
9. 退出领取页时不要无条件删除，否则跳转登录后会丢失上下文。

选择 `sessionStorage` 而不是 `localStorage` 的原因：

- 只在当前标签页有效。
- 关闭标签页后自动清理。
- 不会长期保留已经发放的兑换码。

禁止事项：

- 不把兑换码写入 Pinia 持久化插件、LocalStorage、错误监控上下文或埋点参数。
- 不把兑换码继续放进 `/auth?redirect=...`。
- 不在控制台打印完整兑换码。
- UI 中只显示掩码，例如 `YY-AK**-****-9DSM`。

### 6.3 新增领取页

建议新增：

```text
front/client/src/views/ClaimView.vue
```

页面是独立任务页，不放在工作台壳层中，不显示复杂导航。移动端优先，因为闲鱼买家主要从手机打开。

页面状态：

| 状态 | 页面表现 | 可执行操作 |
| --- | --- | --- |
| `initializing` | 正在检查领取信息和登录状态 | 无 |
| `missing_code` | 没有待领取兑换码 | 手动输入备用码 |
| `invalid_format` | 兑换码格式不正确 | 重新输入 |
| `unauthenticated` | 默认显示注册，允许切换登录 | 注册并领取、登录并领取 |
| `authenticated` | 回显当前账号和领取内容 | 领取到此账号、切换账号 |
| `claiming` | 正在领取，按钮锁定 | 不允许重复提交 |
| `success` | 显示新增次数和当前余额 | 开始创作 |
| `invalid` | 兑换码无效 | 输入备用码、联系卖家 |
| `used` | 兑换码已使用 | 若属于当前账号则展示已领取，否则提示联系卖家 |
| `expired` | 兑换码已过期 | 联系卖家 |
| `network_error` | 网络异常 | 重试 |
| `service_error` | 服务暂不可用 | 重试、保留待领取码 |

### 6.4 登录与注册复用

优先复用现有认证 Store 和 API，不复制一套认证逻辑。

可以采用以下任一代码结构：

1. 将 `AuthView.vue` 中登录/注册表单抽成可复用 `AuthForm.vue`，在 `/auth` 和 `/claim` 共用。
2. 在 `/claim` 中嵌入精简表单，但登录和注册调用必须继续走 `useAuthStore()`。

推荐第一种，避免两套表单校验和错误文案逐渐不一致。

领取上下文中的差异文案：

```text
普通注册：创建账号
领取注册：注册并领取 10 次

普通登录：进入工作台
领取登录：登录并领取 10 次
```

注册或登录成功后的逻辑：

```text
认证成功
  -> 重新确认 auth.user 存在
  -> 从 sessionStorage 读取待领取码
  -> 自动调用兑换接口
  -> 成功后更新 entitlement Store
  -> 清除待领取码
```

注册成功但兑换失败时，账号已经创建成功。页面必须显示“账号已创建，领取暂未完成”，并提供“重新领取”，不能让用户重复注册。

### 6.5 已登录账号回显与切换

登录状态恢复成功后显示：

- 当前账号邮箱。
- 兑换码掩码。
- 本次可领取次数；如未实现预检接口，则显示“领取后以实际到账为准”。
- “领取到此账号”主按钮。
- “切换账号”次按钮。

“切换账号”执行：

```text
保留 sessionStorage 中的待领取码
  -> 调用 POST /api/auth/logout
  -> 清理前端用户和权益状态
  -> 当前页面切换到登录表单
```

### 6.6 API 与 Store

在 `front/client/src/services/api.ts` 增加或复用：

```ts
entitlementApi.previewRedemption(code)
entitlementApi.redeem(code, idempotencyKey)
```

现有 `redeem()` 已调用：

```http
POST /api/redemptions/claim
Idempotency-Key: <客户端生成的稳定键>
Content-Type: application/json

{"code":"YY-AKK9-XD9M-9DSM"}
```

在 `front/client/src/stores/entitlement.ts` 中复用现有幂等键管理和余额刷新逻辑。相同兑换码在网络结果未知时必须重用同一个幂等键，不能每点一次就生成新键。

成功后：

- 更新 `entitlement.balance`。
- 刷新次数流水。
- 删除 `yy_pending_redemption_code`。
- 不要再打开原有 `RedeemModal`。

## 7. 后端设计

### 7.1 必须保留的服务端权威边界

无论前端展示什么状态，最终兑换必须由服务端完成以下校验：

1. 用户会话有效且账号状态正常。
2. 兑换码存在。
3. 兑换码未使用、未禁用、未过期。
4. 兑换码适用于当前产品；若现有业务已经使用 `product_code`，必须补齐此校验。
5. 当前请求满足幂等约束。
6. 兑换码状态变更、次数增加、领取记录和幂等结果在同一个数据库事务中完成。

前端不能根据 URL 中有 `code` 就认为兑换成功，也不能自行增加余额。

### 7.2 复用现有兑换接口

正式领取继续使用现有接口：

```http
POST /api/redemptions/claim
```

请求：

```json
{
  "code": "YY-AKK9-XD9M-9DSM"
}
```

响应继续返回：

```json
{
  "code": 0,
  "data": {
    "added": 10,
    "entitlement": {
      "balance": 12,
      "canCreate": true,
      "status": "active"
    }
  }
}
```

当前 `backend/internal/redemption/service.go` 已具备事务、行锁、一次性使用、账号绑定、次数流水和幂等记录。不要另写一套“URL 兑换”业务逻辑；领取页只改变入口，不改变兑换的核心语义。

### 7.3 建议新增兑换码预检接口

为了在用户注册前显示“可领取 10 次”，建议新增一个不消耗兑换码的预检接口：

```http
POST /api/redemptions/preview
Content-Type: application/json

{"code":"YY-AKK9-XD9M-9DSM"}
```

选择 POST 而不是 GET 的原因是避免兑换码再次出现在 API URL、代理访问日志和浏览器网络历史中。

成功响应：

```json
{
  "code": 0,
  "data": {
    "valid": true,
    "credits": 10,
    "productName": "AI 生图 10 次",
    "maskedCode": "YY-AK**-****-9DSM",
    "expiresAt": "2026-09-30T15:59:59Z"
  }
}
```

异常响应应使用统一错误结构，但不要返回兑换用户邮箱、用户 ID、完整兑换码或内部数据库 ID。

预检接口要求：

- 可在未登录状态调用。
- 只读，不创建领取记录，不改变兑换码状态。
- 按 IP 限流，例如每分钟 20 次，并沿用项目已有 RateLimiter。
- 查询时使用现有标准化方法和 HMAC 摘要查找，不做明文全表搜索。
- 无效、禁用等不应泄漏过多内部信息。
- 预检结果不代表最终成功，正式领取时必须再次完整校验。

如果第一期不开发预检接口，前端仍可完成快捷流程，只是注册前不能可信地显示具体次数。此时文案必须写“注册后领取本兑换码额度”，不能仅根据闲鱼文案硬编码 10 次。

### 7.4 登录会话

继续使用现有 HttpOnly Session Cookie：

- Cookie 只能通过 HTTPS 传输，生产环境 `Secure=true`。
- Cookie 保持 `HttpOnly=true`。
- `SameSite=Lax` 适合从闲鱼链接顶层跳转到网站后使用本站 API。
- 前端 HTTP Client 继续使用 `withCredentials=true`。
- 用户勾选“保持登录”时使用持久 Cookie；未勾选时使用会话 Cookie。
- `/api/auth/session` 是前端回显登录用户的依据。

不允许为快捷兑换把 Session Token 返回到 URL、LocalStorage 或响应 JSON 中。

### 7.5 管理端库存导出

在现有兑换码批次生成或导出能力上增加“闲鱼自动发货库存”导出格式。

每个未使用兑换码输出一行：

```text
浏览器打开领取并开始创作吧～：https://img.daidaiweb.cn/claim?code={urlEncodedFullCode} ｜ 兑换码：{fullCode}
```

要求：

- 只能导出管理员有权查看的完整兑换码。
- 一行对应一个兑换码，不得把同一个码输出两次。
- 默认只输出当前仍可用的兑换码。
- UTF-8 编码。
- 导出动作写入管理审计日志，记录批次、数量和管理员，不记录完整兑换码正文。
- 下载响应和服务日志不得打印导出文件内容。
- 域名做成后端配置，例如 `PUBLIC_WEB_URL=https://img.daidaiweb.cn`，不能在多处硬编码。

## 8. URL 中携带完整兑换码的安全补救

本方案已确定使用 `?code=完整兑换码`，因此必须明确：前端清理地址栏只能减少后续暴露，无法阻止首次请求已经经过 Cloudflare、Nginx 或其他反向代理。

上线前至少完成以下措施：

1. `/claim` 响应设置 `Referrer-Policy: no-referrer`。
2. `/claim` 页面不要在兑换码清理前加载第三方统计、客服、广告或错误监控脚本。
3. Cloudflare、Nginx 和应用访问日志对 `/claim` 不记录 Query String，或将 `code` 参数脱敏。
4. 错误监控的 URL 采集配置必须删除 `code` Query 参数。
5. 前端埋点只记录 `claim_opened`、`claim_success` 等事件，不记录兑换码。
6. 页面初始化后立即将地址改为 `https://img.daidaiweb.cn/claim`。
7. HTML 设置 `Cache-Control: no-store`，避免带码页面响应被中间层缓存。
8. 禁止把完整领取 URL放进站内分享、复制链接或二维码历史功能。

这些措施无法让 Query 方案达到一次性随机领取票据的安全级别，但属于采用该方案后的最低上线要求。

## 9. 异常与恢复规则

### 9.1 重复打开同一链接

- 未兑换：允许继续正常流程。
- 已被当前账号兑换：如果后端能够确认归属，显示“你已领取过”，并展示当前余额。
- 已被其他账号兑换：显示“该兑换码已使用”，不得泄漏对方账号信息。

### 9.2 注册成功但兑换响应丢失

前端保留原兑换码和原幂等键，再次请求。后端必须回放第一次成功结果，不得重复加次数。

### 9.3 网络中断

- 不清除待领取兑换码。
- 页面提供“重新领取”。
- 不自动无限重试，避免重复请求和用户困惑。

### 9.4 用户刷新页面

- 地址栏已经没有 `code`。
- 从当前标签页 `sessionStorage` 恢复兑换流程。
- 如果兑换已经成功并已清除待领取码，则进入成功页或普通手动领取页，不再次兑换。

### 9.5 用户关闭标签页

`sessionStorage` 随标签页关闭而清除。用户可以重新点击闲鱼中的原始链接恢复流程。

### 9.6 兑换码过期、无效或禁用

- 清除当前待领取码。
- 展示明确状态。
- 提供“输入备用兑换码”和“联系卖家”。
- 不允许前端自行更换或猜测兑换码。

## 13. 测试要求

### 13.1 前端单元与组件测试

3. 能从 `sessionStorage` 恢复待领取流程。
4. 已登录时正确回显邮箱，不显示密码和 Token。

### 13.2 后端测试

1. 预检有效兑换码只返回允许字段，不改变数据库状态。
2. 预检无效、禁用、过期和已使用兑换码符合约定。

4. 同一兑换码只能成功一次。

7. 事务中任一步失败时，兑换码状态和余额全部回滚。
8. 兑换成功绑定当前用户并创建次数流水。
9. 日志和审计记录不包含完整兑换码。
10. 管理端导出一行一码，URL 与备用码匹配。

2. 未登录老用户登录并领取。
3. 已登录用户确认账号并领取。

## 14. 验收标准

满足以下全部条件才可交付：

1. 闲鱼库存只需预生成完整领取消息，不修改 Helper。
2. 新用户无需复制兑换码，注册后自动领取。
3. 老用户无需复制兑换码，登录后自动领取。

6. 兑换成功后显示新增次数和服务端返回的当前余额。
7. 重复点击、刷新和网络重试不会重复增加次数。
8. 兑换码和次数始终绑定账号，由服务端校验。
9. 原右上角手动兑换入口仍可使用。
10. Query 参数不会进入应用日志、错误监控、统计埋点和后续页面 URL。
11. OpenAPI、Mock、真实后端和前端类型保持一致。
12. 自动化测试通过，并完成真实移动端浏览器流程验收。
